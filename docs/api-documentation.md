# REST API Contract

## 1. Status and source of truth

This contract documents the implemented authentication, customer, debt, payment, reversal, and reporting routes. `GET /api/health` is the liveness endpoint. The contract follows `backend/prisma/schema.prisma`, [Requirements](./requirements.md), and [Database design](./database-design.md). If this document and the Prisma schema disagree about persisted fields or enum values, the schema is authoritative; business rules in the requirements and database design remain authoritative for validation.

All paths below are relative to the existing `/api` global prefix. IDs are UUID strings. JSON property names are camelCase, matching Prisma model fields. Fields generated by the server (IDs, actor `userId`, status, and timestamps) are read-only unless a route explicitly describes an action.

## 2. Wire conventions

### Money and quantities

- Every monetary value is a JSON **string**, never a JSON number: `"125.50"`. Do not use exponent notation. This preserves PostgreSQL `Decimal(18,2)` exactly and avoids JavaScript floating-point arithmetic.
- Monetary input has at most 16 integer digits and up to two fractional digits. Responses are decimal strings; trailing zeros may be omitted by Prisma's decimal serializer. Values must be positive for debt, payment, and allocation amounts; item unit price and subtotal may be zero as allowed by the database design.
- Item quantities are decimal strings with up to 15 integer digits and three fractional digits (for example `"1.250"`), corresponding to `Decimal(18,3)`.
- Calculate totals, allocations, and balances with decimal arithmetic on the backend, never binary floating point. Reject values that exceed the database precision or cannot be represented at the field's scale. Each quantity × unit-price item subtotal is rounded half-up to two decimal places before summing.
- The application displays Philippine peso (`PHP`, `₱`). Amounts remain decimal strings in the API; clients format them for the selected language/locale without changing their value.

### Dates and time zones

- Datetime fields are RFC 3339 timestamps with an explicit offset on input (for example, `"2026-11-02T03:30:00Z"`). Responses use UTC with `Z`. They represent instants stored as PostgreSQL `Timestamptz(6)`.
- `occurredAt` is the debt event time; `paidAt` is when payment was received; `createdAt` / `updatedAt` are server record timestamps. Omitted event timestamps default to the server's current time.
- Date-only report filters are calendar dates, not UTC instants. Convert them to an inclusive start and exclusive end (`[from, to + 1 day)`) in the report's IANA time zone. `Asia/Manila` is the default business time zone. Clients should send a `timeZone` when date-based reporting must be unambiguous.
- `archivedAt` is either `null` or an RFC 3339 timestamp.

### Common response and collection shapes

Successful single-resource requests return the resource JSON directly. Collection requests return:

```json
{
  "data": [],
  "pagination": {
    "page": 1,
    "pageSize": 25,
    "totalItems": 0,
    "totalPages": 0
  }
}
```

Unless stated otherwise, list endpoints accept `page` (1-based, default `1`) and `pageSize` (default `25`, maximum `100`). Out-of-range values are validation errors. The default ordering is newest first, with UUID as a stable tie-breaker; customer lists default to name ascending. Cursor pagination and configurable sorting are **TBD**.

## 3. Prisma-aligned resources

The persisted enum values are exact and case-sensitive:

| Prisma enum | Allowed values |
| --- | --- |
| `TransactionType` | `MONEY_LOAN`, `STORE_ITEMS` |
| `TransactionEntryMode` | `ITEMIZED`, `TOTAL_ONLY` |
| `TransactionStatus` | `ACTIVE`, `VOIDED`, `REVERSED` |
| `PaymentStatus` | `POSTED`, `VOIDED`, `REVERSED` |

`User` has `id`, `name`, `username`, `passwordHash`, `role`, `createdAt`, and `updatedAt`. Never expose `passwordHash`. `Customer` has `id`, `name`, nullable `contactNumber`, nullable `notes`, nullable `archivedAt`, `createdAt`, and `updatedAt`.

A transaction response includes `id`, `customerId`, `userId`, `type`, nullable `entryMode`, `totalAmount`, `status`, nullable `description`, `occurredAt`, `createdAt`, `updatedAt`, and `items`. Each item has `id`, `transactionId`, `itemName`, `quantity`, `unitPrice`, `subtotal`, and `createdAt`. `userId` is assigned by the authenticated server context, not accepted from the client.

A payment response includes `id`, `customerId`, `userId`, `amount`, nullable `paymentMethod`, nullable `notes`, `status`, `paidAt`, `createdAt`, and `allocations`. Each allocation has `id`, `paymentId`, `transactionId`, `allocatedAmount`, and `createdAt`. `userId` is server-assigned.

## 4. Authentication

The API uses username/password credentials with bcrypt password hashes and one-hour JWT bearer tokens. Send the token in `Authorization: Bearer <token>` for protected routes. The frontend keeps the token in tab-scoped session storage and clears the session after an authenticated request returns `401`.

| Method and path | Purpose |
| --- | --- |
| `POST /auth/login` | Authenticate with `{ "username": "...", "password": "..." }`. Return `{ accessToken, tokenType: "Bearer", expiresIn: 3600, user }`. |
| `GET /auth/me` | Return the authenticated safe user object; return `401` when unauthenticated. |

Launch uses a single owner login; employee accounts and role-based permissions are deferred. Public registration and password reset are out of scope initially. The authenticated server context supplies `userId`; clients cannot choose or override the acting user. Do not expose records until authentication is enforced on protected routes.

The Prisma `UserRole` enum reserves `OWNER` and `EMPLOYEE`; launch authorization permits the single owner account. Employee provisioning and restricted permissions are introduced only in the later employee-roles phase.

## 5. Customers

| Method and path | Purpose |
| --- | --- |
| `GET /customers?q={text}&includeArchived=false` | List/search customers. `q` is an optional trimmed partial search over name (case-insensitive) and contact number (case-sensitive). Exclude archived customers by default. |
| `POST /customers` | Create `{ "name": "...", "contactNumber": "...", "notes": "..." }`. Name is required; nullable fields may be omitted or `null`. |
| `GET /customers/{customerId}` | Read the profile. |
| `PATCH /customers/{customerId}` | Update supplied profile fields (`name`, `contactNumber`, `notes`); omitted fields remain unchanged. `id`, timestamps, balances, and financial history are not writable here. |
| `POST /customers/{customerId}/archive` | Set `archivedAt`; hide from the default list, but retain customer and financial history. |
| `POST /customers/{customerId}/restore` | Clear `archivedAt` and return the customer to the default list. |
| `GET /customers/{customerId}/balances` | Return the category-separated and combined balances described below. |

Archiving hides the customer from the default list, but retains the profile and financial history for lookup. Archiving does not delete or alter transactions/payments, prevents new debt, and still allows payments against existing debts.

## 6. Debt transactions

| Method and path | Purpose |
| --- | --- |
| `POST /customers/{customerId}/transactions` | Create one debt transaction. |
| `GET /customers/{customerId}/transactions` | List that customer's history; supports pagination and filters `type`, `status`, `from`, and `to`. |
| `GET /transactions/{transactionId}` | Read a transaction with its item snapshot and, where useful, allocations. |
| `POST /transactions/{transactionId}/void` | Void an erroneous debt with no posted allocations; retain the record and audit the action. |
| `POST /transactions/{transactionId}/reverse` | Reverse a debt after reversing any payments allocated to it; retain the original record and audit the action. |

Create payloads:

```json
{
  "type": "MONEY_LOAN",
  "totalAmount": "500.00",
  "description": "Optional",
  "occurredAt": "2026-11-02T03:30:00Z"
}
```

```json
{
  "type": "STORE_ITEMS",
  "entryMode": "ITEMIZED",
  "items": [
    { "itemName": "Rice", "quantity": "2.000", "unitPrice": "50.00" }
  ],
  "description": "Optional",
  "occurredAt": "2026-11-02T03:30:00Z"
}
```

For `STORE_ITEMS` with `TOTAL_ONLY`, send `entryMode: "TOTAL_ONLY"`, positive `totalAmount`, and optional `description`; do not send item rows. The total-only request shape is:

```json
{
  "type": "STORE_ITEMS",
  "entryMode": "TOTAL_ONLY",
  "totalAmount": "175.00",
  "description": "Small purchases",
  "occurredAt": "2026-11-02T03:30:00Z"
}
```

Rules:

- `MONEY_LOAN` has no entry mode and no items. Omit `entryMode` and `items`; reject an incompatible supplied value.
- `STORE_ITEMS` must specify `ITEMIZED` or `TOTAL_ONLY`. `ITEMIZED` requires one or more items; each `itemName` is required, each quantity is positive, and each unit price is nonnegative. Zero-value item prices are allowed. The server calculates each subtotal and `totalAmount` using exact decimal arithmetic. A client-supplied total is not authoritative.
- `TOTAL_ONLY` requires a positive `totalAmount`; it has no item rows. Description is optional.
- Created transactions start as `ACTIVE`. Clients cannot set status, `userId`, IDs, allocation totals, or audit data.
- The schema has no hard-delete route. Financial corrections retain the original record, set its status, and write an audit entry. A void identifies an erroneous entry; a reversal cancels an otherwise valid entry. Both stop affecting the balance. Reverse or void allocated payments before voiding/reversing their debt; do not change a debt while posted payment allocations remain.

## 7. Payments and explicit allocations

| Method and path | Purpose |
| --- | --- |
| `POST /customers/{customerId}/payments` | Record a payment and its full allocation atomically. |
| `GET /customers/{customerId}/payments` | List payment history with pagination and optional `status`, `from`, and `to` filters. |
| `GET /payments/{paymentId}` | Read a payment and its allocations. |
| `POST /payments/{paymentId}/void` | Void an erroneous payment, retain its record and allocations, and audit the action. |
| `POST /payments/{paymentId}/reverse` | Reverse a posted payment, retain its record and allocations, and audit the action. |

Example request:

```json
{
  "amount": "150.00",
  "paymentMethod": "cash",
  "notes": "Optional",
  "paidAt": "2026-11-02T03:45:00Z",
  "allocations": [
    { "transactionId": "11111111-1111-4111-8111-111111111111", "allocatedAmount": "100.00" },
    { "transactionId": "22222222-2222-4222-8222-222222222222", "allocatedAmount": "50.00" }
  ]
}
```

Allocation rules:

1. A payment must contain one or more explicit allocation lines; no amount may remain silently unallocated, and the sum of `allocatedAmount` values must equal `amount` exactly.
2. Every target must be an `ACTIVE` transaction belonging to the same customer as the payment. The allocation may span `MONEY_LOAN` and `STORE_ITEMS` transactions; the category is derived from each target transaction, never inferred from the payment.
3. Each allocation must be positive and no greater than the target transaction's outstanding amount. Do not allow overpayment/credit or allocation to a voided/reversed transaction.
4. A payment cannot contain duplicate `transactionId` lines. This matches the Prisma unique key on `(paymentId, transactionId)`.
5. Create the payment and all allocations in one database transaction. Concurrent requests must not cause an over-allocation; the exact locking/serialization implementation is an API implementation concern.

Payments start as `POSTED`; clients cannot create or edit allocations by directly changing payment status. Only allocations on `POSTED` payments reduce debt balances. Voiding or reversing a payment removes its allocations from the effective balance without deleting the original payment or allocation records, and writes an audit entry.

Archived customers may still make payments against their existing debts. Customer archival blocks new debt entries but does not prevent settlement.

## 8. Balances, history, and reports

### Balances

`GET /customers/{customerId}/balances` returns decimal strings, for example:

```json
{
  "customerId": "11111111-1111-4111-8111-111111111111",
  "moneyLoan": "100.00",
  "storeItems": "50.00",
  "combined": "150.00",
  "asOf": "2026-11-02T04:00:00Z"
}
```

An outstanding transaction balance is `totalAmount - sum(valid allocated amounts)`. Category balances sum outstanding amounts for `ACTIVE` transactions by `MONEY_LOAN` and `STORE_ITEMS`; the combined balance is their sum, not a replacement for the category balances. Only allocations associated with `POSTED` payments count. Reversed or voided payments no longer reduce debt balances. A transaction can be reversed only after all payments allocated to it are reversed.

### History

`GET /customers/{customerId}/transactions` and `/payments` provide distinct debt and payment histories. The response may embed allocations in payment records and allocation/payment summaries in transaction records, but must preserve direct links by ID. Include status, event timestamp, and monetary values so the history can be reconciled. The current schema has no dedicated immutable audit-event read endpoint; whether to expose `AuditLog` entries is **TBD**.

### Reports

Implemented first-release routes:

| Method and path | Purpose |
| --- | --- |
| `GET /reports/summary?asOf=...` | Total outstanding, `MONEY_LOAN`, and `STORE_ITEMS` totals. |
| `GET /reports/customers?asOf=...` | Per-customer category-separated and combined outstanding summaries; supports pagination/search. |
| `GET /reports/daily?from=YYYY-MM-DD&to=YYYY-MM-DD&timeZone=Asia/Manila` | Daily summaries over a calendar-date range. |
| `GET /reports/monthly?from=YYYY-MM&to=YYYY-MM&timeZone=Asia/Manila` | Monthly summaries over a calendar-month range. |

These routes report debt records created, payment allocations received, and outstanding balance as separate measures with `MONEY_LOAN`, `STORE_ITEMS`, and combined totals. Debt/payment flow values are gross records entered during the period, including records later voided or reversed; period-end outstanding uses the record status as of that period end, reconstructed from audit timestamps. Summary outstanding includes archived customers' balances; the paginated customer report hides archived customers. Daily reports accept at most 90 days and monthly reports at most 24 months, with `Asia/Manila` as the default IANA time zone. Never sum debt and payment flows as though they were the same measure.

## 9. Search, filters, and validation

- Customer search uses the `q` parameter against name (case-insensitive substring) and contact number (case-sensitive substring). Customer transaction history filters by exact enum `type` and `status`; history/report date filters use event dates (`occurredAt` for transactions, `paidAt` for payments).
- Unknown query parameters may be rejected. Invalid UUIDs, enum values, date formats/ranges, page bounds, missing fields, extra body fields, and incompatible transaction fields are client errors. The existing NestJS global `ValidationPipe` enables transform, whitelist, and rejection of non-whitelisted fields; DTOs should implement this contract.
- Check customer existence, target transaction ownership, status, remaining balance, exact allocation sum, and decimal precision on the backend. A rejected financial write must be atomic and leave no partial payment/allocations.

Proposed validation response (`400`):

```json
{
  "statusCode": 400,
  "code": "VALIDATION_FAILED",
  "message": "Request validation failed.",
  "details": [
    { "field": "allocations[0].allocatedAmount", "code": "OUTSTANDING_EXCEEDED", "message": "Allocation exceeds the transaction balance." }
  ],
  "requestId": "optional-correlation-id"
}
```

Use the same top-level error shape for other failures. Proposed status/code mapping:

| HTTP | Example code | Meaning |
| --- | --- | --- |
| `400` | `VALIDATION_FAILED` | Malformed or invalid request / business validation failed. |
| `401` | `UNAUTHENTICATED` | Missing or invalid credentials. |
| `403` | `FORBIDDEN` | Authenticated user lacks access. |
| `404` | `NOT_FOUND` | Resource not found or intentionally not disclosed. |
| `409` | `CONFLICT` | Duplicate, stale, or incompatible state (including idempotency conflict). |
| `500` | `INTERNAL_ERROR` | Unexpected server failure; do not return stack traces or secrets. |

NestJS currently returns its standard exception response; a stable error-code registry and request-ID mechanism are not yet implemented.

## 10. Idempotency and duplicate-submit protection

For financial create requests (`POST` transaction and payment routes), clients should send an `Idempotency-Key` header containing a unique opaque key for one user action and reuse the same key on retries. The server should atomically associate the key with the authenticated actor, route, request fingerprint, and result:

- Same key and same request within 24 hours: return the original result without creating a second debt/payment.
- Same key with a different request: return `409` with a standard NestJS conflict response.
- New key: process the request once; persist the idempotency record with the financial write.

The Prisma `IdempotencyRecord` persists keys per authenticated user for 24 hours. The server uses a request fingerprint, returns the persisted response for a matching retry, and rejects reuse with a different request. Expired keys may be reused when submitted again. Disabling a submit button in the UI is useful but is not a substitute for server-side duplicate protection. The payment's payment-allocation uniqueness constraint alone does not prevent duplicate payment records. Expired-record cleanup should be configured before production.
